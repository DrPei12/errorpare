# Model Catalog Integration Validation

## Goal

Validate whether `Model-catlog-builder` can reduce model configuration work inside a real AI developer tool, without forcing a full backend or admin console migration.

## Integration path used

ErrorPare adopted the smallest path from the package:

- import the model configuration core
- generate an app-specific normalized catalog snapshot
- generate an ErrorPare-friendly routing config
- wire the existing CLI config flow to that catalog

This validation intentionally did **not** mount the starter API or `/admin` UI. The point was to test whether the package still adds value inside a CLI-first product.

## What was integrated

### 1. Local package import

`ErrorPare` now depends on the local package:

- `model-catlog-builder` via `file:../Model-catlog-builder`

### 2. Catalog refresh script

`npm run models:refresh` now:

- reads the normalized catalog generated by `Model-catlog-builder`
- adapts provider IDs to ErrorPare naming
- keeps legacy-only providers when the package does not cover them yet
- writes generated snapshots into `src/core/model-config/generated`

### 3. Runtime adapter

`src/core/model-config/catalog.ts` now gives ErrorPare a small app-facing surface:

- list provider entries
- get the default provider/model selection
- list recommended/latest models by provider
- read resolved routing defaults

### 4. Embedded onboarding wiring

`errorpare init --analyze` now uses the imported package for the real end-user setup flow in interactive terminals:

- launch the curated terminal onboarding
- limit choices to providers ErrorPare can actually execute today
- validate credentials before saving
- persist encrypted credentials under `~/.errorpare/model-catalog`
- write the chosen provider/model back into ErrorPare's own `config.json`

`errorpare config` now also surfaces:

- catalog source
- env var
- recommended models
- routing defaults and fallback refs
- the model-catalog profile path and source provider metadata when onboarding was used

## What this proves

This integration now proves four parts of the package's core value:

1. developers can remove hardcoded provider/model tables from their app config flow
2. developers can keep app-specific provider naming through a thin adapter layer
3. end users can complete provider/model/API-key setup through the embedded onboarding instead of app-specific prompts
4. the host app can still keep ownership of actual provider execution logic

## What still required app-specific adaptation

The integration still needed a small adapter layer because provider identities do not always match 1:1:

- `google` in the package becomes `gemini` in ErrorPare
- `qwen` in the package becomes `bailian` in ErrorPare

This is a useful validation result. The package solves normalization, but real products still need a final app-specific mapping layer.

## Current limitations found during validation

### 1. The embedded onboarding only exposes providers that ErrorPare can execute today

That is intentional. The package has a wider catalog than ErrorPare's current analyzer adapters.

The embedded flow currently focuses on:

- OpenAI
- Anthropic
- OpenRouter
- Gemini
- Qwen/Bailian
- DeepSeek
- Moonshot/Kimi

Providers outside that set still need ErrorPare execution support before they should appear in the onboarding menu.

### 2. Importing generated catalog JSON increases bundle size

The current CLI build pulls the generated catalog snapshot directly into the bundle. That is acceptable for validation, but if ErrorPare wanted to productionize this path, it would likely want:

- a smaller curated export
- or a runtime-loaded JSON file instead of bundling the full snapshot

### 3. App-side execution adapters still matter

The package improved selection and routing, but ErrorPare still owns provider execution behavior:

- Anthropic message format
- Gemini API shape
- OpenAI-compatible providers

That separation is healthy. The package should keep solving configuration, not hide provider-specific inference calls.

## Recommendation

This path is worth continuing.

The next useful step is to tighten the package around this integration shape:

- smaller curated catalog export
- an officially supported adapter pattern for provider ID remapping
- a documented "CLI/app config only" import path
- a first-class embeddable credential handoff helper for host applications

That would make it even easier for tools like ErrorPare to adopt the package without pulling in the full starter surface.
